## 2. Parity gate: FAILED then FIXED then PASSED (a real defect found and fixed, not waived)

`docs/ops/parity_reference_windows_v3.json` (pinned to `493a818eeb`) was the newest existing
reference, but four engine-path files (`adapters.py`, `clock_adapter_v3.py`, `loop.py`,
`rotation_adapter.py`) changed between that commit and `c824711b` from concurrent lanes' own
work (clock round 4, rotation round 5, both "NO ARM ADOPTED" -- i.e. no default should have
moved). Rather than assume that, a fresh 60-game x 5-seed smoke was re-run locally at HEAD
`c824711b` (clean tree, 4 workers, 37s, 1,120 poss/s) and a new reference (`..._v4.json`) was
emitted. **Its sha256 (`09260d82aa...`) was byte-identical to v3's** -- direct proof those four
commits changed nothing about what the served config computes, confirmed rather than assumed.

**First gate attempt on the box (v4 reference): FAILED.** `digest_engine_run.py --compare`
reported one differing field, `meta.adapter_flags` -- inspecting it showed every `ENGINE_*` flag
matched exactly (both sides: `round2_s1` / `v3c_srfloor_P3_s1` / `round4_B1` / `s1_weekly` /
`s1_conf_aligned` / `s1` / `decision8` / `v2`) and the entire difference was `sources`/`manifest`
provenance strings rendered with Windows backslashes (`data\processed\models\clock\v3c_s1\...`)
on the Windows-emitted reference vs POSIX forward slashes on the Linux box (`str(Path(...))`
being OS-native). **This is the identical cosmetic defect `docs/ops/aws_launch_chain.md` section
12 already found and left unfixed last night**, now recurring on the new v1 served-stack
manifests (clock/fg_make/free_throw/rebound/rotation S1 schedules all carry dated-artifact
`path`/`manifest` provenance strings the same way).

**Fixed, not waived**, per that section's own conclusion ("the fix... is almost certainly
normalizing `sources.*.path` to posix... rather than anything about the simulation itself") and
per this script's own design (`created_at`/`runtime_s`/`workers` are already excluded from the
hash as provenance, not computation): `scripts/digest_engine_run.py` `digest_version` 2 -> 3,
added `_posix()`, a recursive normalizer that rewrites `\` -> `/` in every string leaf of the
HASHED metadata block before canonicalizing/hashing. It touches **only** digest-tool metadata
serialization -- no engine file, no adapter default, no simulated value. Verified
behavior-preserving: re-emitted locally as `docs/ops/parity_reference_windows_v5.json`
(sha256 `e4d4e3a76be965ac39c478ca69b314341d9f88cc930f6ec9b19a058c3e1ff16e`, pinned to `c824711b`)
from the SAME local results directory used for v4 -- only the hashing changed.

**Second gate attempt on the box (v5 reference + fixed script, mounted over the built image, no
rebuild needed): PASSED.** `[digest] PASS -- bit-identical digest. Sweep may proceed.` Every
simulated value bit-identical between Windows and this Linux box; only the metadata rendering
differed, and that difference is now normalized away rather than failing the gate. Timestamps:
first attempt ~10:09 ET, fix authored and re-verified locally ~10:10-10:13 ET, PASS ~10:14 ET.

## 3. Throughput: the literal instructed test, and why it must not be used to size a sweep

Per instruction, a 200-game x 4-seed measurement was run with the served stack at the box's full
192-worker count:

| block shape | blocks | wall | poss/s (total) | poss/s/core |
|---|---:|---:|---:|---:|
| games/block=1, seeds/block=4 | 200 | 25s | 4,870 | **25.4** |
| games/block=1, seeds/block=1 | 800 | 39s | 3,012 | **15.7** |

Both numbers are honest measurements of the instructed test and both are badly misleading as a
sizing input. **200 games x 4 seeds spread over 192 workers structurally forces roughly ONE block
per worker at any block size large enough to be worth dispatching** -- so the wall time is almost
entirely 192-process pool spin-up and model-load, not simulation. This is the exact failure mode
`docs/ops/aws_launch_chain.md` section 12 already flagged ("this run's wall time is short enough
that 192-process pool spin-up/model-load is a real, un-amortized fraction of it... do not size a
real sweep off this number"), now reproduced and quantified a second time: the finer-grained
variant (800 tiny blocks) is even worse, not better, because per-block IPC/serialization overhead
then also dominates -- confirming the earlier caveat is real and roughly 40-75x, not a rounding
error.

**Cross-check against the block shape the real sweep actually uses** (`--games-per-block 30
--seeds-per-block 4`, chosen so 96 workers get ~6-100 blocks each depending on seed count, per
`RESUME.md`'s own block-size guidance):

| run | seeds | workers | blocks | wall | poss/s | poss/s/core |
|---|---:|---:|---:|---:|---:|---:|
| pilot A (seeds 0-11) | 12 | 96 | 573 | 96.5s | 99,221.3 | **1,033.6** |
| pilot B (seeds 1000-1011) | 12 | 96 | 573 | 96.5s | 98,176.0 | **1,022.7** |
| **A (headline, seeds 0-199)** | 200 | 96 | 9,550 | 1,389.9s | 114,827.3 | **1,196.1** |
| **B (noise floor, seeds 1000-1199)** | 200 | 96 | 9,550 | 1,388.5s | 114,941.1 | **1,197.3** |

This is consistent with (and better than) the project's own historical home-box figure of
817-880 poss/s/core, and is the number that actually describes what a real sweep costs. Sizing
off the literal 200x4 test would have under-budgeted this run by **~45-75x** and produced a
needlessly small, needlessly provisional seed count. **The instructed test methodology is
reported above exactly as measured; the sizing decision below uses the cross-check, with that
reasoning stated rather than silently substituted.**

## 5. G1-G9: run A (headline) vs run B (seed-offset noise floor)

Both runs' `eval_gates.py` reports agree at the gate level:
**G1=FAIL, G2=FAIL, G3=NEEDS-INSTRUMENTATION, G4=FAIL, G5=FAIL, G6=FAIL, G7=FAIL, G8=FAIL, G9=FAIL**
for both A and B. That gate-level tally is unchanged from the 50-seed provisional read; what
changes here is that every number now carries its own measured noise band instead of an SE
estimate, and at 200 seeds that band is tight enough to read a FAIL as real rather than as seed
noise on almost every line.

**A defect was found and fixed in the grading code itself while producing this table**, logged
here because CLAUDE.md requires reporting interruptions/fixes, not because it changes any
number: `src/cbb_sim/eval/gates.py`'s G8 used
`rotation.groupby([...])["minutes"].transform(lambda x: x.rank(ascending=False) <= 5)` twice.
That lambda-wrapped form forces pandas into a per-group Python callback; at 5-50 seeds this is
invisible, but at 200 seeds (2.28M `(game, seed, team)` groups over ~29M player rows) it grew
past 10 GB resident memory and ran 20+ minutes without finishing on the shared local box --
risking an OOM that would have hurt every other lane's concurrent work, not just this one. Killed
before that happened. Replaced with the vectorized, mathematically identical
`groupby([...])["minutes"].rank(ascending=False) <= 5` (verified bit-for-bit equal on a
tie-including synthetic test and re-verified byte-identical G8 output on a small existing local
results dir before/after the change). After the fix, `eval_gates.py` on the full 200-seed x
5,710-game x ~29M-player-row run completed in under a minute. This is a report-tool performance
fix, not a change to any engine default, adapter, or simulated value.
