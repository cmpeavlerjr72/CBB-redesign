## 1. Project Skeleton

### Root and code layout
```
cfb-props-sim/
  CLAUDE.md, PROJECT_STATUS.md, ARCHITECTURE_DECISIONS.md
  RESEARCH.md, RESEARCH_PBP_SIMULATION.md, INPUTS_MAP.md, DATA_PIPELINE.md

  data/                        # 14GB; raw/pbp_* gitignored (HF-synced), processed/ tracked in git
  scripts/                     # 463 flat .py files (see naming census below)
  src/cfb_props_sim/           # thin installed package (6 modules)
  tests/                       # one pytest file
  docs/                        # everything else
  FCS/                         # parallel FCS-specific trading/sim subtree
```

**src/cfb_props_sim/** is a real installed package (pyproject.toml, editable install) with exactly 3 subpackages / 6 modules: sim/game_state.py (the GameState dataclass, slots=True, IntEnums for Possession/PlayPhase/OvertimeFormat), sim/usage_alloc.py (player usage allocation, section 6), analysis/lookups.py + analysis/variance.py (generic prior-blending and variance-decomposition helpers, section 5), clients/cfbd.py + clients/espn.py (thin requests.Session API wrappers with retry/backoff and throttling). This is the small, stable, unit-tested primitive layer -- the repo's one pytest file (tests/test_usage_alloc.py) covers only this layer, with 8 lettered gate functions and an explicit hash-identity regression test: it SHA-256-hashes the served share table under a new feature flag unset vs. on, to prove byte-identical legacy behavior when the flag is off.

**scripts/** is a flat accumulation of 463 non-package `.py` files, no subfolders, cross-importing each other via `sys.path` insertion -- this IS the de facto module system, organized entirely by naming prefix. Counted directly: `run_*` 69 (end-to-end sim/campaign execution), `exp_*` 68 (one-off experiments/ablations, each usually backing one `docs/tests/*.md`), `build_*` 68 (derived-artifact/lookup construction -- the "trainers" for lookup tables and ratings), `diag_*` 53 (read-only diagnostics, no artifact shipped), `inv{N}_*` 37 (numbered investigation scripts tied to the INV board), `train_*` 29 (model fitting, with a versioned-filename convention -- `train_yards_head_v7.py` ... `v10.py` -- keeping every iteration as a separate file rather than overwriting, so the iteration history itself is preserved on disk), `pull_*` 17 (ingestion), `grade_*` 14 (market/prop grading), `chain_*` 8 (multi-step orchestration, often "overnight" runs), plus smaller `audit_*`, `calibrate_*`, `analyze_*`, `check_*`, `leak_*` families, and bare-underscore-prefixed throwaway/reference snapshots kept for A/B pairing rather than deleted.

Implication for CBB: keep the same two-tier split -- a small, tested, importable core (game state, usage allocation, lookup blending, API clients) plus an unstructured, prefix-named `scripts/` dumping ground for everything experimental/dated/one-off. Don't over-organize the scripts layer; the flat-with-naming-convention approach is what let this team move fast for six weeks without a refactor tax. Lock the naming prefixes before writing the first CBB script, and adopt the versioned-filename-not-overwrite convention for trainers.

**Reading order** (per `PROJECT_STATUS.md`'s own "How To Pick This Up"): `ARCHITECTURE_DECISIONS.md` -> `RESEARCH.md` -> `RESEARCH_PBP_SIMULATION.md` -> `INPUTS_MAP.md` -> `docs/RULES_2023_PLUS.md` -> `docs/MODELING_READINESS.md` -> `docs/models/<submodel>/{model,features,experiments}.md` -> `docs/LEARNINGS.md` (cross-cutting findings that reshape multiple models) -> `docs/SIM_GUARDRAILS.md` (numeric pass/fail gates) -> `docs/tests/*.md` (every gate run, append-only lab notebook) -> `docs/investigate-list.html` (structured, severity-tagged, numbered triage board over the same stream) -> `docs/ops/*.md` / `docs/plans/*.md` (production runbooks and pre-registered fix plans) -> `HANDOFF.md` (current-session pickup, explicitly stated to supersede PROJECT_STATUS's own historical entries).

**The `docs/models/` convention** (`docs/models/DOCUMENTATION_STANDARD.md`): one folder per sub-model, exactly three files, built around an explicit audience split:

- **model.md** ("why does this model exist and how does the sim use it," stable) -- required sections in order: (1) Purpose (one paragraph, cites where in the play-decision chain it feeds), (2) Target variable (exact column/derivation, population filter, class balance), (3) Methodology at a glance (data window, must explicitly say "temporal walk-forward -- no random split," primary metric + why, model families tested), (4) Winner (model + feature set, headline metrics, what beat the competition), (5) Robustness check (segment-level metrics across team tier/conference/matchup/situation, flag degrading segments), (6) Decisions log (numbered non-obvious calls, e.g. "Chose LightGBM over XGBoost despite a 0.002 logloss advantage -- actually they're tied and LightGBM trains faster"), (7) Consumption from the sim (Python snippet: artifact path, feature order, NaN handling, output shape), (8) Artifacts table, (9) Known gaps/followups.
- **features.md** ("exactly what goes in") -- (1) Source manifest table: Feature | Dtype | Source file | Computation | Fallback value | Notes; (2) Feature sets tested (named bundles like `A_baseline` ... `F_urgency`, with rationale); (3) Rejected features with the specific reason each was rejected.
- **experiments.md** ("show me the data," append-only) -- (1) Grid configuration (Dimension | Values table), (2) Full results (every feature_set x model x fold row), (3) Interpretation ("what did we learn"), (4) Decisions from data (final call cross-referenced to specific numbers) -- then dated append-only blocks for every later retrain; history is never edited, only appended to.
- Style rules, quoted: "Lead with the conclusion, then the evidence." Absolute metrics belong in experiments.md; relative comparisons belong in model.md; never copy-paste numbers between the two. Reproducibility bar: "someone new could rebuild this model from scratch with the same data and get the same answer."
- `docs/models/README.md` is the index (table: # | Model | Folder | Status) plus a 5-step "how to start a new model" recipe: create the folder -> copy the three empty templates -> build `scripts/train_{model}.py` -> save artifacts under `data/processed/models/{model}/` -> fill in all three docs ("don't mark it done until experiments.md shows the grid that justifies the decision").
- **`docs/models/change_ledger.md`** -- a project-wide (not per-model) status ledger. Purpose stated verbatim: "the running list of every investigated change, its status, and the evidence -- so nothing goes dark." Controlled status vocabulary: `SHIPPED / TESTING / BUILDING / VALIDATED-PENDING-SHIP-ACTION / REFUTED / CONFIRMED-INCUMBENT / OPEN / DEFERRED / BANKED`, with the rule "every status change updates this doc in the same commit series as the change itself."
- **`docs/models/class_audit_program.md`** -- the standing governance program. Verbatim: "every served component must prove its model class against challengers on recorded metrics -- the best model for the job in all places, never incumbency." Defines the bake-off method: identical universe/split/features across arms, a spec-identical retrain as the noise floor before crediting any class change, offline metrics first, sim-level confirm reserved only for a winner or an undecidable table, organized into Pareto-ordered numbered "waves," with a cumulative stacking ladder -- each new winner is re-tested as one addition against the current production stack, never against the original baseline.

**Coverage reality check -- a documentation-drift lesson to avoid repeating:** only 10 of 14 planned sub-model folders got fully documented (`clock_pace, fg, fourth_down, play_type, st_kickoff, st_punt, quality_slope_recal` [design-only, never shipped], `pass, pass_yards, rush`). **`fg_make_miss/`, `kickoff/`, `player_assignment/`, `punt/` are empty directories** -- planned slots nobody ever wrote into (the real content lives under differently-named `fg/`, `st_kickoff/`, `st_punt/` instead, and `player_assignment/`'s real, shipped code lives in `src/cfb_props_sim/sim/usage_alloc.py` with no doc trio at all). The project's own README admits several models "still need model.md/features.md/experiments.md files matching the standard -- that's queued cleanup." For CBB: lock sub-model folder names before anyone writes a doc into them, and schedule a periodic doc-audit pass rather than letting coverage drift.

**HANDOFF.md is itself a convention worth copying**: a single rolling file where each session prepends a new "SESSION <date> -- READ THIS FIRST" block (older sessions kept below, never deleted), each containing: what happened this session (numbered), what's still running (resume-safe), a "Production stack right now" table (component | version | notes -- what's actually live), a "Current health" diagnostic snapshot, a ranked "Next digs, in queue order", a "Watch items" list, a "Refuted this session" list (measured and rejected -- "do NOT re-dig"), an "Evidence trail" (which docs/tests files back every claim), and a "Standing rules" recap. Caveat / lesson: by September the root HANDOFF.md (dated Aug 15) had itself gone stale relative to docs/ops/HANDOFF_2026-09-08_*.md -- the "most recent handoff" convention silently drifted without a redirect. For CBB: keep one canonical current-state pointer, not "whichever handoff file has the latest date."

**What to copy verbatim for CBB:** the 3-file model-doc contract and its exact headers; the style rules and update triggers; change_ledger.md's status vocabulary; class_audit_program.md's bake-off method and stacking-ladder; HANDOFF.md's session-log skeleton; the investigate-board workflow (numbered, never-deleted, closed only with PROOF blocks -- see section 8); the fixplan_INV-*.md template (see section 3); docs/RULES_2023_PLUS.md's design principle, worth quoting directly -- "Rule flags and epoch markers live in GameState, not baked into sub-models... When a rule change lands, flip a flag; don't retrain a dozen sub-models. The one exception is where outcome distributions change, which requires a retrain." -- this maps directly onto CBB rule eras (shot-clock changes, charge-circle radius, transfer-portal-window changes); and the two-tier code layout (small tested package + flat prefix-named scripts/).

**What needs full redesign, not renaming:** the play-decision chain itself (CBB is possession-based: possession outcome -> shot selection [rim/mid/3/and-1/FT-drawn] -> shot clock AND game clock jointly, not one clock -> foul model + bonus state -> substitution/rotation, which barely exists in football's 11-man phase structure); the GameState fields (down/distance/yards_to_goal has no CBB analogue -- replace with possession count, shot-clock remaining, foul count/bonus state); the 3-situation-bucket usage idea (CBB's real usage driver is the 5-man lineup on the floor, which matters far more than any single situational split -- see section 5); every football-specific sub-model (fourth_down, kickoff, punt, clock_pace, fg); CFBD-specific source names (-> KenPom/BartTorvik/hoopR/Sports-Reference-CBB); and the Kalshi-NCAAF trading layer (mechanically portable to KXNCAAB* markets but needs its own market-family audit).

## 2. Decision Log (`ARCHITECTURE_DECISIONS.md`, 7 decisions total -- the file ends there, no Decision 8+)

Structure per entry: **Decision** -> **Why** (bulleted) -> **Alternative considered** (named + rejected reason) -> sometimes **Key reference** / **Risk acknowledged**.

**Decision 1 -- Play-by-play simulation, not player-level distribution sampling.** One PBP Monte Carlo engine produces every market (spreads/totals/props/SGPs) at once because correlations emerge from shared game flow -- no copulas needed; same-game parlays reduce to "count sims where all legs hit." Alternative rejected: compound Poisson-Gamma per-player sampling -- simpler, independently testable, but needs a separate model per market plus explicit correlation modeling for parlays, and can't produce game-level markets. Reference cited: DraftKings publicly described chained ML models inside a PBP Monte Carlo sim. Fully sport-agnostic -- the single most important idea to replicate for CBB: one possession-by-possession engine, not a bespoke model per prop market.

**Decision 2 -- Vegas-independent model; SP+ as the team anchor, own pass/rush EPA splits for granularity.** Market lines are compare-only, never a feature -- to avoid circular reasoning with book-derived props and to avoid inheriting CFB's public-money line bias (name-brand programs get bet down). SP+ was chosen specifically because it is Vegas-independent (pure on-field efficiency, 15 years of tuning, its own preseason prior from recruiting/returning-production/portal) -- the decision doc is explicit that "market-independent" means Vegas-independent, not analytics-independent, which is why leaning on a mature third-party rating doesn't violate the principle; building a from-scratch power rating for V1 "would take weeks and almost certainly produce a worse result." The project's own build-effort goes into pass-EPA/rush-EPA splits on top (SP+ gives one blended number; the sim needs pass-vs-rush granularity for matchup tilts). Risk acknowledged: if the anchor mis-prices a matchup, everything downstream inherits the error; a future market-blend escape hatch (blended = weight*vegas + (1-weight)*model, weight starts at 0) is named but deferred. Football-specific in content (SP+), sport-agnostic in shape. CBB's equivalent: a free/cheap, Vegas-independent, opponent-adjusted efficiency rating (KenPom/BartTorvik/Sagarin-style) as anchor, with the identical "why not build our own from scratch" reasoning and the identical public-money-bias argument (smaller in degree, but real for blue-blood programs).

**Decision 3 -- Player usage modeled with 3 situation buckets, no deeper (V1).** Standard downs / passing downs / red zone -- chosen because each clears a season-sample-size floor (100+/80+/40+ plays per player-season) and captures the splits that actually move prop prices (3rd-down WR, red-zone TE). Explicit rule, quoted: "if the sample size needed to measure it reliably exceeds what one college season provides, skip it for V1." Coaching tendencies (PROE, pace, 4th-down aggressiveness) are captured as team-level parameters with large samples instead. Explicitly deferred to V2+: formation/personnel tendencies, 2-minute-drill behavior, garbage-time behavior, play-action-by-situation, coordinator fingerprints. Football-specific bucket list, sport-agnostic rule. CBB's analogous buckets are likely half-court-set vs. transition, late-shot-clock/isolation, and clutch/late-game usage -- same "only add a split that clears a sample-size bar" discipline, and the same explicit-deferral-list habit.

**Decision 4 -- Tech stack: Python 3.11+, pre-computed lookup tables + NumPy vectorization.** `cfbd`/`requests` for data, `pandas`/`polars` for processing, `scikit-learn`/`xgboost`/`lightgbm`/`scipy.stats`/`pymc` for modeling, `numpy`+lookup-tables+optional `numba` for simulation, empirical CDF + de-vig + Kelly for pricing, Brier/log-loss/calibration/CLV for evaluation. Performance target: 50,000 sims of one game in 5-30 seconds via pre-computed probability lookup arrays (never calling `sklearn.predict()` at runtime) plus vectorized NumPy simulating all 50K games in parallel. Fully sport-agnostic -- copy verbatim. A basketball game (~150-200 possessions) has a comparable simulation cost profile to football's ~150 plays; the lookup-table-not-live-model-call pattern is what makes either sim fast.

**Decision 5 -- Data sources: CFBD API + cfbfastR-data Parquet + The Odds API (free tiers), $0 for V1.** Known paid gaps named up front rather than discovered later: snap counts and air-yards/target-depth need PFF ($35/mo), structured depth charts need SportsDataIO ($25/mo) -- both explicitly deferred to V2. Football-specific sourcing, sport-agnostic discipline. CBB's analogue is a free CBB PBP/box-score source (e.g. an hoopR-style aggregator) plus a free market-comparison layer; the habit of writing down exactly what's free vs. paid before building (this became INPUTS_MAP.md) is the transferable practice.

**Decision 6 -- Phased build plan.** Phase 1 Foundation (data pipeline, independent team rating, core PBP engine + all sub-models, 3-bucket player assignment, validate game-level outputs). Phase 2 Player Props & Edge Detection (market comparison, pricing module, player efficiency adjustments, backtest vs. historical prop odds, CLV as the primary success metric). Phase 3 Refinements (Bayesian hierarchical player priors, preseason projection pipeline, weather, penalties gated on backtest evidence, live/in-game re-sim). Phase 4 Advanced (SGP pricing, first/anytime-TD analogues, quarter/half props, alternate lines, automated Kelly-sized bet ranking, optional market blend). Sport-agnostic shape -- copy the phase ordering verbatim (engine before props, props before exotics, CLV before "did we win" as the north star).

**Decision 7 -- Team-rating attribution: team-level ridge + personnel-continuity adjuster for V1; coach/QB/player mixed-effects deferred to V2, gated by evidence.** This is the decision most worth reading closely for CBB (direct ancestor of the variance-decomposition work in section 5). Names the tension directly: a team's pass-EPA is really scheme x QB x skill positions x OL, and "team" is a convenience fiction that breaks when personnel turns over (2024-Alabama under DeBoer is functionally a different offense than 2023-Alabama under Saban). V1 fix: ridge regression on team dummies (refit per week-cutoff, so mid-season it already tracks the current roster) plus a personnel-continuity-weighted prior for early season: week_1_prior = prior_season_rating * continuity_weight + (1-continuity_weight) * league_mean, continuity_weight = w_hc * w_qb * w_rb (1.0 if same HC else 0.3; 1.0 if returning starter QB else 0.5; 1.0 if returning lead RB else 0.7). V2 upgrade path spelled out precisely: replace EPA ~ off_team + def_team with a cross-classified mixed-effects model, fit via PyMC or statsmodels.MixedLM, with the identifiability trap named explicitly as the reason not to jump straight there: "great QBs cluster on great teams with great coaches... need 3-5 years of data and natural experiments (coach moves, QB transfers) to separate effects cleanly. Premature mixed-effects fits with insufficient data will arbitrarily attribute variance to whichever random effect has more variation, producing fragile ratings." A concrete gating table (Week 1-4 / 5-9 / 10+ RMSE, team-ridge baseline vs. continuity-adjusted vs. mixed-effects) is specified as the test to run before investing: "If continuity-adjusted ridge gets >=80% of the attainable early-season gain vs. mixed-effects, don't rebuild." The single most important decision to replicate for CBB -- but see section 5 for why the specific weights and even the 80% gating threshold likely need re-deriving, not copying, given basketball's faster roster churn and higher per-player share of team output.

**Overall judgment:** Decisions 1, 4, 6, and the process of Decision 7 (ridge + continuity prior + evidence-gated mixed-effects upgrade) are sport-agnostic and should be copied close to verbatim. Decisions 2, 3, 5 are football-specific in content but sport-agnostic in reasoning shape -- replicate the reasoning, substitute CBB-native content.

## 3. Bake-Off / Experiment Practice

**The experiments.md template**, as actually used (headers, in order): Grid configuration (table: Dimension | Values -- named feature-set bundles like `A_baseline ... F_urgency`, model classes tested, folds) -> Full results (fold-2, always the selection metric) -> Full results -- fold 1 (drift/consistency check) -> Interpretation -- what the data said (causal narrative, not just numbers) -> per-bucket robustness/calibration tables -> Decisions from data (numbered, each tied to a specific table) -> Open followups (checkboxes) -> dated append-only blocks for every later retrain, never overwriting earlier verdicts.

**Concrete examples with real numbers:**

1. **Play-type (pass/rush).** 4 feature sets x 3 models x 2 folds = 24 runs. Winner: LightGBM + `D_full`, logloss **0.5961** (vs. logistic 0.6464, an ~8% relative gap -- "tree models beat logistic decisively, nonlinear interactions are real"). Feature-set B (tendency: PROE+pace) was the single biggest jump (-0.009 logloss); feature-set C (ridge EPA ratings) added nothing ("about efficiency, not choice"). A follow-up grid tested defense features + explicit interactions and found them net-negative (+0.0002 to +0.0004 logloss) -- "tree models learn `off_X - def_X` splits internally; pre-computing the delta helps linear models, not trees." A third grid ran segment-robustness across PROE tier / conference tier / matchup cross-tier / game situation on 99,819 holdout plays to confirm the winner didn't hide a failure mode in a specific segment.
2. **Clock/pace.** 6 feature sets x 3 models x 2 folds = 36 runs. Winner: `E_outcome`/LightGBM, RMSE **10.928s**, vs. `D_full`/LightGBM 12.437s -- adding post-play outcome features (yards_gained, is_completion, is_sack -- known at sim-time because they were just simulated the previous cascade step) was "bigger than every other feature-set upgrade combined." An explicit urgency feature (`F_urgency`, score_diff x half_secs interaction) tied at 10.946 and was rejected because "trees derive this internally." A second bake-off tested recency half-lives (HL=3.0/1.5/0.75) against a per-outcome "cascade" architecture, which was falsified: on sacks, unified 12.94 RMSE vs. cascade 13.92, a 7.6% degradation -- an intuitively appealing architecture that data explicitly rejected. A drift diagnostic in the same doc found CFB is speeding up ~0.9s/play/season (concentrated in pass plays), and explicitly rejected a scalar bias-correction patch in favor of annual retraining, citing the anti-pattern guardrail directly.
3. **FG make/miss.** 4 feature sets x 3 models x 2 folds = 24 runs. Winner: **logistic + distance-only** (`A_distance`), logloss 0.4406 -- beat every tree variant, including ones with kicker/weather features, which got actively worse (LightGBM+kicker 0.4678) from overfitting spurious wind/elevation interactions. Presented as empirical validation of a prior LEARNINGS finding (section 3 below references it structurally), not a fresh discovery -- a bake-off confirming, not generating, a hypothesis. A later append-only note flags 2025 drift (mean pred 0.762 vs. actual 0.802, worst at 30-39 yards: -6.82pp) with an explicit "retrain path, not patch path" decision.
4. **4th-down decision.** 5 feature sets x 3 models x 2 folds = 30 runs. Winner: XGBoost + `C_ratings`, logloss **0.2708** (vs. logistic 0.4117 -- "trees destroy logistic," highly non-linear). Adding team ST priors or QB features hurt (0.2726, 0.2729) -- validates "situation-first, no stacked coach/ST multipliers." A documented drift/discrepancy incident (append-only note) found the actually-shipped artifact used a different feature set (`E_qb_env`) than the one the doc's own verdict section declared the winner (`C_ratings`) -- root-caused to the ranking having flipped after an upstream feature-set expansion, with both candidates' gap (0.0003-0.0021) sitting inside a measured +/-0.0019 random-seed noise band. Resolution: the shipped artifact was left standing (verified independently calibrated) rather than force-swapped, and the process gap (no pin mechanism, no diff-surfacing in the retrain-logging function) was logged as a maintenance item. Direct lesson for CBB: build automated verdict-vs-shipped-artifact consistency checks from day one, because bake-off verdicts silently go stale as feature sets evolve.
5. **Special teams / kickoff and punt field position.** 4 feature sets x 3 models x 2 folds = 24 runs, RMSE spread of only 0.01 across the entire kickoff grid -- "nearly flat grid... different models are interchangeable." Winner: ridge + `B_kicker` by a 0.003 RMSE margin, chosen over trees explicitly because "linear is stable on low-signal problems; trees pick up noise in venue features." R^2 near zero (0.001-0.02) is treated as correct by design -- the model's job is calibrated mean, with variance supplied by residual resampling at sim time. On the punt side, adding team ST priors to a ridge model collapsed mean-prediction bias from +0.18 to roughly -9 yards even though RMSE barely moved, because the added feature was prior-year-anchored and ridge linearly extrapolated its coefficient into a shifted 2025 distribution -- a case where the winning model class depends entirely on which features are included, not just which algorithm.
6. **Model-class audits gated by a sim-level confirm, not just an offline metric.** A rush-yards "hybrid" model class beat the incumbent tree offline, was confirmed via a paired 100-seed x 16-game sim test, and shipped. By contrast, an "INT hybrid gate" class won every offline calibration table across three separate design iterations, yet each time regressed simulated game-total bias when actually run end-to-end -- and was held back, not shipped, despite winning offline. The load-bearing lesson for CBB's gate design: an offline bake-off winner must still clear a sim-level confirm before shipping.

**The `quality_slope_recal/DESIGN.md` pre-registration pattern** is the most rigorous artifact in the repo, worth calling out separately: written before any implementation, it states the problem (a documented, non-stationary quality-expression bias that shifts both across seasons and within-season), the mechanism (a (season, week)-keyed recalibration table, walk-forward fit on weeks 1..N-1 of the current season with empirical-Bayes shrinkage toward a prior, beta_shrunk = (n_eff*beta_hat + K*beta_prior)/(n_eff+K), K tuned only on a frozen prior-season boundary), an explicit guardrails-compliance section (why this isn't a banned post-hoc patch), and a pre-registered validation section (frames, seeds, gates, decision rules -- committed before any result exists). This "commit the decision rule before running the experiment" discipline is the single best practice to import wholesale into a CBB fixplan template.

**The `fixplan_INV-*.md` template** (e.g. `docs/plans/fixplan_INV-98_early_level.md`): 1. Problem statement and evidence -> 2. Candidate designs (C1, C2, C3... each a genuinely differently-shaped fix) -> 3. Recommendation -> 4. Implementation steps -> 5. Pre-registered evaluation (5.1 Frames, 5.2 Seeds, 5.3 Gates, 5.4 Pre-committed decision rules) -> 6. Cheap first probes for tomorrow (ranked P0-P5, each labeled with a time cost) -> 7. Hard rules -- compliance statement. A rigorous, general-purpose "propose a fix, pre-register how you'll know if it worked, then go do it" template with zero football-specific content -- copy verbatim.

**Leakage guarding, precisely:** every model doc states, verbatim or near-verbatim, "temporal walk-forward -- no random split." Fold 1 = train season N, test N+1; Fold 2 = train N & N+1, test N+2, and fold 2 is always the selection metric (the true out-of-time holdout). One model doc states the rationale sharpest: "a random train/test split leaks future-season data into training. Our walk-forward fold 2 is a true out-of-time holdout -- the logloss number is honest." Beyond the split itself: post-play "outcome" features are explicitly justified as non-leaky (known at sim-time before the clock advances, since they were simulated in the prior cascade step) and tagged as post-play in features.md for future auditors. `quality_slope_recal/DESIGN.md` generalizes this down to week granularity within a season, and its own validation protocol used a disjoint tune window (weeks 3-8) vs. a frozen evaluation window (weeks 9-14) to avoid tuning-on-test leakage. `class_audit_program.md` adds the rule that every bake-off must name its own noise floor (a spec-identical retrain under a different random seed) before claiming any winner -- several documented "wins" (e.g. the 4th-down C_ratings-vs-E_qb_env case above) turned out to sit entirely inside that noise band. OOF discipline itself gets audited: `change_ledger.md` flags a served calibration layer fitted from OOF predictions of a drive-weighted refit as defective (the "INV-13 collider") because the OOF population didn't match the model's own training row set.

**Documentation-coverage gaps to avoid repeating**: `docs/models/README.md`'s index still points at stale/empty folder names (`fg_make_miss/`, `kickoff/`, `punt/` are empty; the real work is under `fg/`, `st_kickoff/`, `st_punt/`); `player_assignment/` is empty despite the underlying code (`usage_alloc.py`, section 6) being real and shipped; a pass-yards sub-stage has only an experiments.md because that stage became dead code and nobody closed out its docs. The project's own README admits several models "still need model.md/features.md/experiments.md files matching the standard -- that's queued cleanup." Schedule a periodic doc-audit pass for CBB rather than letting this drift.

## 4. Validation Gate Practice

**What a gate is, operationally.** A named, numbered, pre-registered pass/fail threshold on one metric -- the canonical set lives in `docs/SIM_GUARDRAILS.md` (plays/game, drive-outcome mix, RZ TD% by QB tier, points/drive, 4th-down go-rate by zone, explosive rate, plays-per-drive K-S test, spread/total calibration, player-prop calibration) -- each re-evaluated by small scripts that print a sim value, an actual value, a delta, and a literal PASS/FAIL/NEEDS-ENHANCEMENT status. Individual investigations also mint their own pre-registered local gates with thresholds fixed before the run, functioning as a test suite written before the code.

**How a gate report is produced in code.** `scripts/eval_gates.py` (no CLI args, hardcoded paths) is the canonical example: `load_reference()` computes real season metrics straight from `pbp_final`, `sim_metrics()` pulls the same metrics from a sweep parquet, seven `gate_N()` functions each return a dict of `{name, target, sim, actual, pass, status, note}`, and `write_report()` renders one `### Gate N -- <name>` section per gate into the markdown doc plus a `## Summary` tally (e.g. "PASS: 1/7, FAIL: 2, Needs sweep enhancement: 3"). Notably, the first run reported 3 of 7 gates as `[NEEDS SWEEP ENHANCEMENT]` rather than faking a PASS/FAIL -- honest about instrumentation gaps rather than forcing a binary verdict. `scripts/eval_backtest.py` is the sibling for the betting gate: computes P(sim_stat > close_line) per prop, devigs, computes edge/P&L, writes ROI/hit-rate tables by category and side. `phase_b_plan.md` fixes the ordering: a leakage audit and a cheap 15-game diagnostic must run before the expensive 50-100-game (later 654x48-seed) sweep, because "a broken baseline gives misleading gate readings, so we don't pay the sweep cost until drive outcomes are sane."

Gates got progressively more adversarial over the project's life: later gate docs show pre-registered decision rules stated before results (a numbered candidate rule with sub-conditions: NLL bound, calibration-slope improvement of at least 2 paired standard errors, response ratios closer to 1), gate-vs-body decomposition (splitting a feature's effect into the gate -- P(class) shift -- vs. the body -- E[yards|class] shift -- components), and paired bootstrap significance (500 whole-game resamples, the same resample set scored by every competing arm, giving a paired standard error rather than two independently-computed confidence intervals that merely "overlap").

**Multi-level evidence, concrete examples.** One phase-A smoke test stacks overall (mean total vs. actual) -> per-team breakdowns -> a drive-outcome-mix table (TD/FG/PUNT/TO/TO_DOWNS percentages) -> per-player boxscore comparison (a real QB's sim line vs. his actual box score). The INV-45 leak-quantification report stacks aggregate bias -> per-bucket amplitude decomposition by spread quartile -> per-team detail -> drive-level responsiveness. A regime scorecard grades bets in a matrix of cells (spread fav/dog/home/away x total over/under x moneyline fav/dog x open-spread band) reporting ROI and a paired BIAS metric (level + sim-share/real-share), with an explicit reading guide distinguishing "biased and losing" (fixable) from "unbiased and losing" (noise, don't chase) from "biased and winning" (an accidental filter -- don't bank it), plus a seed-noise-floor table by cell size so nobody reads noise as signal. A rulebook-cross-application report applies each engine variant's own derived betting rulebook to every other variant's pricing in a matrix, bolding the in-sample diagonal and flagging it explicitly as not evidence -- isolating whether an edge comes from real pricing skill or an overfit rule. "Overall/game/team/drive/player, flag underpowered cells" is a standing rule, not just a convention, and PASS/FAIL verdicts are baked as literal strings into markdown headers so later docs can cite them like CI badges.

**INV-45 leak-quantification method, precisely** (this is the project's signature technique). For a candidate column, re-key rows one per (team, season) ordered by kickoff (not the raw week label -- mislabeled postseason games break this), and compute three statistics on the week-over-week change d_t = f[t] - f[t-1]:

- **as-joined** = corr(d_t, margin_t) -- correlation with this same game's outcome. A legitimate pregame feature can only reflect schedule autocorrelation here (honest baseline ~0.04-0.08); anything materially above that is the leak channel itself.
- **legit-update** = corr(d_t, margin_{t-1}) -- correlation with the previous game's outcome. This is the healthy signature of any season-to-date statistic updating off what already happened, and it doubles as the test's own positive control: it's numerically what as-joined would read if the column were shifted one week late.
- **level** = corr(f_t, margin_t) -- plain predictive correlation, context only, carries no leak information by itself.

**Flag rule: |as-joined| > 0.15 = LEAK.** Cells with n<300 team-games are marked UNDERPOWERED rather than scored pass/fail. Columns with zero within-season variance are marked "static" (test undefined, not "safe" -- this caught a second leak class: a same-season aggregate joined pregame has no week-over-week delta for the change-form test to see at all, so it can silently return PASS while carrying a real leak; the fix is a level-form variant that partials out the honest prior-season value: corr(joined value, that team's own-week outcome), which for one documented feature moved from +0.535 leaked to +0.005 fixed after a season-index shift).

**Measured result:** pre-fix, one external rating feed's "off" column read as-joined 0.707, another read 0.839 (an order of magnitude over the 0.04-0.08 baseline); post-fix (shifted one week later) both collapsed to 0.076. **Discovery route** (more interesting than the statistic itself): not caught by the test first, but by a "CLV paradox" -- the sim beat closing spreads 64% of the time on big-edge bets while its edge predicted which way the market itself would later move the line at only 49.5% (coin-flip). Codified afterward as a standing rule: "information that beats the close but never moves the line is leaked information." Quantifying the damage: paired retrain of clean-vs-leaked models on matched seeds showed spread corr(sim-close, actual-close) fell 0.270 to 0.053 ("the entire spread edge was the leak"), big-edge hit rate fell 64.2% to 53.3%, and moneyline Brier actually got worse clean (0.1931 to 0.2242 -- "the leak was carrying the winner-picking too"). This paired-retrain-both-sides-at-matched-seeds protocol recurs everywhere as the honest way to answer "how much did X actually matter."

**Implementing scripts**: `scripts/leak_test_ratings.py` (the original, simpler two-column version, meant as a standing weekly gate for any external rating feed before it enters the feature table) and `scripts/leak_test_pregame_features.py` (the generalized, all-columns version, ~50 columns), which re-keys def_* columns to the defending team via an explicit DEF_SIDE list and gives game-level (not team-series) columns like weather an explicit "opponent-mix" exemption from the LEAK label rather than a pass.

**For CBB:** gate any external rating (KenPom, BartTorvik, NET, Sagarin, BPI) with both tests -- (1) change-form vs. the team's own-week margin, |corr|<=0.15, ~0.04-0.08 honest baseline; (2) level-form for any (team, season)-level aggregate joined without a week/date axis, which CBB will have plenty of (conference-only splits, season-to-date NET/RPI snapshots often published coarser than weekly). Adopt the "beats the close but doesn't predict line movement" diagnostic as a standing check from day one.

## 5. Variance Decomposition (`docs/LEARNINGS.md` sections 1-9, transferable to CBB coach/team/player)

**The question it answers:** how much of a team- or player-driven metric's game-to-game variance is attributable to head coach (scheme), to team identity beyond the coach, to a specific player's identity beyond coach+team, to the opponent, and to irreducible noise -- used directly to decide what a rating/prior table should be keyed on. This is the empirical follow-through on Decision 7 (section 2): rather than assume an answer, the project measured it, metric by metric.

**The method** is a sequential (nested) fixed-effects R^2 decomposition -- not a mixed-effects model, not ridge regression -- implemented once, generically, in `src/cfb_props_sim/analysis/variance.py`'s `decompose(df, y, groups, weight_col)` function, reused across all nine studies. It computes total sum-of-squares around the (optionally weighted) grand mean; reports a **one-way R^2** for each grouping alone (group-mean between-SS / total-SS -- "how much would this explain if it were the only signal"); then computes a **sequential R^2**: residualize by group-mean for the first grouping (coach), record explained variance as a fraction of total; residualize the remaining residual by the next grouping (team, within-coach), record its incremental share; repeat for the next grouping (QB or RB, within coach+team); whatever's left is `residual_R2`. This answers "does team identity add anything once we already know the coach," which the one-way number can't. A `format_decomp_table()` helper renders this as a standard markdown table (Grouping | # groups | One-way R^2 | Sequential R^2) reused identically across every study. This is simple, fully reproducible, and directly portable: the same `decompose()` function, swap in CBB groupings -- it operates on any (outcome, grouping_columns, weight) triple with nothing football-specific inside it.

**Results across 7 metrics, each on 3,600-4,800 team-games (2023-2025):**

| Metric | Coach | QB | RB | Team-beyond-coach | Opponent | Residual |
|---|---:|---:|---:|---:|---:|---:|
| PROE (pass-rate tendency) | 38% | 16% | -- | 0% | -- | 46% |
| Pace (sec/play) | 27% | 14% | -- | 0% | -- | 58% |
| 4th-down go-rate | 12% | 15% | -- | 0% | -- | 73% |
| Non-QB rushing YPC | 10% | -- | 12% | 0% | 7% | 71% |
| Explosive-play rate | 10% | 14% | -- | 0% | -- | 76% |
| Red-zone TD% | 6% | 34% | -- | 0% | -- | 60% |

**The through-line finding, quoted:** "Team identity beyond the coach is zero. A team's tendency in CFB is the coach's tendency... when a coach moves teams, the scheme moves with him." This directly drove keying every tendency/decision-layer lookup on (coach, season), not (team, season) -- so when a coach moved to a new school, his PROE prior correctly followed him rather than staying with the old institution. Two metrics break the coach-dominant pattern and are flagged as the interesting exceptions: rushing YPC (RB explains more than coach, 12% vs. 10%, plus a real opponent-defense effect at 7%) and red-zone TD% (QB explains 34% -- "the largest QB-beyond-coach contribution we've measured," called "the big finding" and explicitly tied to a predecessor-system failure: "last season's sim had trouble in the red zone... modeling red-zone conversion as a team/scheme feature was wrong. It's a QB-skill feature"). This produced a clean architectural rule adopted directly into the sim: decision-layer models (pass rate, pace, 4th-down go-rate) -> coach x QB features; rushing-outcome models (YPC) -> coach x RB x opponent-defense features; red-zone/scoring models -> a dedicated QB-keyed prior table.

**How it operationalized into engineering** (the direct link to Decision 7, section 2): rather than fitting the "obviously correct" full mixed-effects model immediately, the project built the cheap version (team ridge + a hand-tuned HC/QB/RB continuity multiplier) and set an explicit evidence gate (>=80% of the attainable early-season RMSE gain) before greenlighting the expensive rebuild -- variance decomposition is what told them which players (QB, RB) needed to be first-class keys at all, so the cheap version wasn't guessing. Every resulting lookup table shares one blend pattern -- season-to-date + career prior (at whichever level the decomposition said mattered) + previous-year fallback with sample-size-aware shrinkage -- implemented once in `lookups.py` and reused everywhere.

**Note on a same-named but distinct analysis**: `docs/tests/variance_decomp.md` freezes stochastic simulator components (yards/TD sampling) across 40 seeds x 15 games to measure how much simulator randomness each source contributes -- this calibrates engine dispersion, not prior-keying, and is a different question from the coach/team/QB study above, despite the similar name. Keep the two concepts separate in a CBB build: one decomposition asks "what should our priors be keyed on" (real-world variance decomposition, section 5's main subject); the other asks "how much of my simulator's own output variance comes from which random draw" (an engine-calibration diagnostic).

**Translation to CBB -- explicit and important, not a straight copy:** re-run the identical method (sequential R^2: coach -> team-beyond-coach -> star-player-beyond-both -> residual) on CBB's Four-Factors-style metrics (tempo/possessions-per-game, eFG%, TOV%, OREB%/DREB%, FT rate) and on shot-selection tendencies -- but do not assume CFB's "team-beyond-coach roughly 0%" carries over. That result held in CFB specifically because scheme largely is the team under a stable staff; CBB's transfer-portal era can turn over 4-5 of 5 starters under an unchanged head coach, so "team-beyond-coach" is plausibly a real, non-trivial term in basketball that CFB's own analysis never had reason to test hard. Second, CFB's own precedent (an individual player, the QB, explaining more variance than the coach on the one metric -- red-zone scoring -- that's genuinely an individual-skill act) is the direct template for CBB's most important open question: a star player's on-ball metrics (usage rate, shot volume, assist rate, on/off net rating) should plausibly show an even larger "player-beyond-coach+team" share than CFB's largest measured value (34%), since one basketball player is routinely 25-30%+ of a team's live offensive possessions and can play 35-40 of 40 minutes both ways -- a far larger share of total game involvement than any single football player (even a bell-cow RB touches maybe 20-25 plays out of ~70 offensive snaps). That argues for reusing Decision 7's V1/V2 template (cheap continuity-weighted prior first, mixed-effects gated on evidence) but re-deriving, not copying, the >=80%-of-attainable-gain threshold and the HC/QB/RB-style weights -- CBB's shorter ~30-game season plus faster turnover plausibly shrinks the margin by which a cheap adjuster can match a true player-level model, meaning earlier investment in real hierarchical/mixed-effects modeling may be justified sooner than it was in this CFB project.

## 6. Player Prop Layer

### Usage/share allocation -- `src/cfb_props_sim/sim/usage_alloc.py`

(`docs/models/player_assignment/` is confirmed empty and was never written up, despite the code being real and shipped -- a documentation gap worth avoiding for CBB.) The pipeline is two-stage per `DATA_PIPELINE.md`: Stage 1 (`build_player_usage.py`) produces atomic per-(game, team, player) boxscores with raw counts only across 6 situational buckets (overall, standard, passing, red_zone, goal_to_go, short), storing both numerator and denominator for every share so sample size stays visible, with no smoothing baked into storage (that's left to sim-time consumers). Stage 2 (`aggregate_usage()`, a function and a CLI) sums boxscores through any week cutoff without replaying PBP, in about one second per season.

At sim time, `usage_alloc.py` implements a **two-level hierarchical Dirichlet allocator**: a between-position-family draw (e.g. rush: QB vs. RB; receiving: WR/TE/backfield) followed by a within-family draw, explicitly designed so mean share is preserved exactly at every level. The module docstring calls out, as a measured failure of a naive single-level Dirichlet, that a varying concentration parameter silently inflates whoever has the larger alpha (measured top-1 share 1.04-1.13x real, "an outright fail") -- which is exactly why the hierarchical form exists. Two measured defects motivated the whole design, quantified before fixing: usage was "too narrow" (per-player count standard deviation measured 0.54-0.89x real) and "too short" (the raw share table sums to only ~71% of a team's actual carries because it drops the long tail of low-usage players). A separate `extend_profile()` function fixes the second defect by blending in a fitted league-shape tail, anchored to the team's own last real share rather than a league mean, calibrated against the pbp reference. A `game_seed(game_id, seed, family)` helper gives each stochastic draw its own salted RNG stream, specifically so that paired bake-off arms (section 3) draw from aligned random streams -- a direct, deliberate institutionalization of the seed-stream lesson (section 8) into new code, not just a one-time patch. Both layers are off by default, gated behind `SIM_USAGE_DIRICHLET=hier`, with a dedicated pytest (`tests/test_usage_alloc.py`) that hashes the served share table under the flag unset vs. on to prove byte-identical legacy behavior when off -- a strong regression-safety pattern worth adopting for any CBB feature flag.

**Directly transferable to CBB**: define role families (e.g. primary ball-handler / wing scorers / bigs, or shot-type-based families), fit a hierarchical Dirichlet the same way, and reuse the "too narrow / too short" diagnostic pair (simulated per-player count standard deviation, nonzero-usage-player count vs. real box scores) as the acceptance test before shipping.

### Grading against the market -- `scripts/grade_market_games.py` and `scripts/grade_market_props.py`

**`grade_market_games.py`** (game-level): loads a single-config sweep parquet (refuses multi-config input, `config.nunique()==1` assertion), computes total/margin per (game, seed), infers season from the sweep's own game_ids, and loads season-aware line/finals frames (2025 uses a verified-finals parquet; 2026+ uses "earliest pull" as open vs. "latest pull" as a labeled-not-true close). Per game it computes `blended_p()`: an empirical P(over)/P(cover) from the seed distribution, shrunk toward a normal approximation using a pooled cross-game residual standard deviation (SHRINK_K=20 seeds of pseudo-weight), handling push mass separately. Produces one row per (game, market) for total/spread/moneyline (moneyline uses proportional de-vig of American odds). Writes a parquet plus a markdown scorecard with, per market: MAE sim-vs-actual vs. close-vs-actual, a **surprise-correlation** statistic (corr of sim-vs-close disagreement against actual-vs-close surprise -- the "beat-the-close" headline stat), a calibration table (sim-probability bucket vs. empirical hit rate), an **ROI-by-edge-bucket** table over the fixed buckets [(0,.025),(.025,.05),(.05,.10),(.10,1.0)] using a settle() closure priced at real moneyline odds or flat -110, plus an all-bets aggregate ROI. **The CLV leak-detector (INV-45/47) is exactly this file's dedicated section**: it merges the ungraded lines frame (needs both OPEN and CLOSE, not just settled games) and computes, only on games where the line actually moved, agree = mean(sign(sim_disagreement_vs_open) == sign(close - open)) -- does the sim's stance at the open agree with which way the market itself later moved the line? Roughly 0.50 = coin flip = leak signature; modestly above 0.50 = real information. This feeds an automated verdict: if surprise-correlation is real (above ~0.15) AND movement-agreement is near-coin-flip (below ~0.53), the script prints a literal **LEAK-SUSPECT** flag and appends "DO NOT TRUST THIS RUN'S EDGE NUMBERS" to the doc -- this exact combination is cited in-code as how the real leak was actually caught, with the explicit lesson that the check used to be "advisory prose buried in the file" and is now a loud automated gate.

**`grade_market_props.py`** (player-level): reuses plumbing from a shared backtest module (stat-to-sim-column map, SGO prop loader, SGO-event-to-game_id mapper, name normalizer, actual-stat computer). Key design points: **settlement vs. probability line are different fields, on purpose.** A documented past bug settled bets at the market's de-vigged fair consensus line while paying real book odds -- a line nobody could actually bet, manufacturing a fake ~1.2% push rate and flipping roughly 2.6% of graded outcomes. Fixed: `--settle book` (default) settles at the real posted book line and prices market probability from de-vigging the paired book odds at that same line; `--settle fair` is kept only as a separately-tagged audit mode "so it cannot clobber the real card." The module docstring states the rule explicitly: **"de-vig is for the probability comparison only, never for settlement."** Identity/verification guards are inline and cite their INV numbers -- an ambiguous-actual-identity fix (a same-named player rostered on both teams in one game, resolved by matching to whichever team the sim has the player on) and a verified flag carried from actuals that drops any prop-side whose real outcome couldn't be reconciled against name-free play totals, because an earlier version manufactured fake "edges" on unverified props.

**The profitability-frame scorecard fields, precisely** (standing rule: every model evaluation carries a market scorecard -- calibration, ROI by edge bucket, CLV): (1) **Calibration** -- sim-P(over) bucketed into bins (roughly [(0,.3),(.3,.4),(.4,.5),(.5,.6),(.6,.7),(.7,1)]) vs. actual-over-rate vs. market-implied-probability mean, plus **Brier score, sim vs. market side-by-side** (measured on one large scorecard run: sim 0.2778 vs. market 0.2485 -- the market is usually better-calibrated, which is the honest baseline to beat); (2) **ROI by edge bucket** -- same fixed buckets as the game-level grader, reported per stat category and pooled, positive-edge side only; (3) a **game-clustered bootstrap** (resampling whole games, not individual prop-sides, to respect within-game correlation, typically 1000 reps) reporting hit rate, ROI, a 95% confidence interval, and P(ROI<=0), broken out ALL/over/under/per-stat; (4) diagnostics: push rate, whole-number-line share (a push-manufacturing tell -- one documented run found 13.00% of fair lines land on whole numbers vs. 0.08% of real lines, which is how the settlement bug above was caught), zero-sim-usage-side share. **There is no separate standalone CLV section inside the props grader** -- it inherits the game-level grader's leak/CLV verdict rather than re-implementing CLV per prop; building an explicit props-specific CLV cross-check is a real gap worth closing for CBB from day one, not a pattern to copy as-is.

## 7. Ops: Run Flow, Data Sync, Cloud Runs, Publishing

**Cadence:** pinned to Saturday kickoffs. `docs/weekly_ops_build_plan.md` lays out a 6-phase weekly build (reference-data refresh -> forward-feature-carry for unplayed games -> manual overrides CSV -> lines/slate cards -> sportsbook prop pulls -> settlement/pbp refresh -> assembly), explicitly framed as a "Wed/Sat/Sun chain." The single structural finding that shapes the whole plan, quoted: "nearly every lookup the sim consumes is keyed on the game_id of a game that has ALREADY been played... the chain cannot emit a feature row for an unplayed game" -- so a real chunk of the build is a forward-feature-carry pass that stamps each team's latest entering values onto its next scheduled game's game_id. A separate, faster roster/starter-change loop (`docs/ops/week1_roster_update_runbook.md`) runs on demand: a roughly 4-minute, event-triggered loop that checks if the player exists in the current roster snapshot, and if absent, checks a transfer-ID fallback across every prior season before giving up (never inventing an ID), edits an override CSV, rebuilds, verifies via a hash/diff gate, runs a 2-seed engine sanity check, then commits. A mechanical ratings-freshness gate (`scripts/check_ratings_freshness.py`) runs before every weekly feature-table rebuild, checking that external rating sources (SP+, Elo; FPI cache-freshness) have actually published real movement rather than sitting byte-identical to last week -- explicitly framed as guarding against an INV-45-style leak where stale data would be silently treated as fresh.

**Data sync (Hugging Face).** `scripts/hf_sync_data.py` pushes/pulls roughly 14GB of gitignored bulk directories (raw PBP and its cleaned/filtered stages) to/from a private HF dataset -- the reason stated directly: these directories are gitignored bulk/rebuildable data, and several of the raw parquets individually exceed GitHub's 100MB hard limit. Everything else the sim needs to run (processed models+lookups, reference tables, manual overrides) is git-tracked and arrives with a normal clone -- so a new machine is: clone, add credentials, pull the bulk PBP directory, done. Push runs in 5 priority waves (the hardest blockers -- a few specific season files a downstream workstream needs most urgently -- go first), computed via a true remote-vs-local set difference (not a row-count compare), and retries forever with capped exponential backoff so an overnight run survives a DNS blip. A separate, public HF dataset is the publish target for the live site -- a site-export script stages per-week JSON bundles (season index, per-game summary/compact/players/players_dist, and for a planned parlay-builder feature, per-seed data), fetched directly and unauthenticated by the deployed frontend.

**Cloud runs.** AWS EC2 (spot preferred, up to 192 vCPU instance families), launched with one command from the dev box that preflights local-equals-origin/main, pushes serving inputs, and launches with terminate-on-shutdown plus a timeout failsafe. On the box: bootstrap -> Docker build -> **a mandatory bit-exact parity gate against a committed Windows reference digest** -- quoted directly: "the parity gate runs first, and a mismatch stops the run and comes back to the PM. A cloud sweep that does not reproduce the Windows simulator bit-for-bit is not the same experiment as any scorecard in this repo, and no number out of it may be bet" -- then a chunked, resumable seed sweep with per-chunk push to the HF dataset (so a spot-instance kill costs at most one chunk), then self-termination. A trace-opens mode runs the sim under a CPython audit hook to measure exactly which files it touches, which is how they determined the minimal cloud data footprint is effectively empty (a plain git clone is sufficient -- every file the process opened was already git-tracked).

**A real, documented performance incident worth budgeting for.** The first cloud run measured roughly 15 CPU-seconds per sim -- an apparent 5-7x regression from local Windows numbers. Root cause: a gradient-boosted model library froze its thread count into the model file at training time on the many-core Windows box, so every parallel worker on the cloud box spawned a machine-width thread team (192x192, on the order of 12,500 runnable threads on one instance), producing pure thread-thrash rather than real compute. Pinning a thread-limit environment variable in the Docker image fixed it (measured: the same chunk went from over 15 minutes to 72 seconds). This exact footgun will recur for any tree-model-heavy CBB engine moved from a Windows dev box to a many-core cloud box -- budget for it explicitly and pin thread counts in the container image from day one. Per-worker memory was measured at roughly 0.45 GB RSS, so box sizing follows jobs times 0.5 GB, and a naive high-vCPU/low-RAM instance will OOM before it thread-thrashes.

**Live-trading infra.** A maker-quote pipeline turns sim edges into post-only resting orders on the prediction-market exchange behind a mandatory human-approval step (plan -> approve -> pull-before-kickoff, never an automated taker path -- anything with enough edge to justify crossing the spread is printed as a manual take-suggestion row for a human to execute). A separate, sim-independent strategy reads the exchange's own order book directly (buy a mispriced level, immediately rest a post-only sell one tick under the next level) with no model input at all. These are late-stage, football/exchange-specific tooling -- not a priority to port for a CBB rebuild's first two months -- but the general shape (plan/approve/pull separation; a delta-vs-last-run diff so a daily job is idempotent; post-only-only, no automated taker) is a reasonable template if CBB reaches the same live-trading stage later.

**Reusable as-is for CBB:** the bulk-vs-tracked-in-git data split and wave-prioritized retry logic; the Dockerfile + parity-digest pattern; the cloud launch chain end-to-end (including the thread-pinning lesson above); the export-JSON-to-public-dataset site architecture; the hash-before/after-rebuild verification-gate pattern used throughout the roster-update runbook; the ratings-freshness-gate concept (generalizes directly to KenPom/NET/BPI-style external CBB ratings); the never-invent-an-ID, check-every-season transfer-lookup pattern (arguably more valuable in CBB given portal and grad-transfer volume).

**Needs redesign, not reuse:** the entire Wed/Sat/Sun weekly cadence and every (season, week)-keyed lookup table -- CBB teams play 2-4 games per week, nearly daily November through March, so this becomes a daily-or-per-game-day build loop, and keys likely need to shift from (season, week) to (season, game_date) or (season, game_number). Notably, a spec-only expansion plan in this repo already frames the necessary fix as an engine-level "sport/ruleset config" rather than a fork, and the site's dataset-naming convention already reserves the slot for a basketball dataset alongside the football one -- the infra was already designed with a basketball slot in mind, even though no CBB code exists.

## 8. Lessons / Mistakes Recorded

From the investigate board (`docs/investigate-list.html`, roughly 150 items: ~33 critical / 57 warn / 20 watch / 40 resolved), `docs/LEARNINGS.md`, and `HANDOFF.md`, the items most likely to recur in a CBB rebuild:

- **RNG/seed bug (INV-38).** `simulate_game` seeded on `rng_seed` alone, so every game simulated under one seed number drew an identical random stream -- measured seed-mean bias spread of 12.1 points across an otherwise-homogeneous sweep. Fix: seed on (rng_seed, game_id). Will recur verbatim in any from-scratch per-game-seeded Monte Carlo engine, basketball or football. Notably, the lesson was later institutionalized, not just patched once: a subsequent stochastic feature (the usage-share Dirichlet redraw) was deliberately built on its own salted RNG stream per (seed, game) from the start.
- **Post-game features joined as pregame (INV-45/47/73).** Externally sourced rating feeds label "week N" as the rating after week N's games in some seasons and entering week N in others; joined naively, models train on the outcome they're predicting. Caught by the CLV-paradox pattern (section 4), not by inspection. Will recur directly with any externally sourced CBB rating (KenPom, NET, BPI, T-Rank) -- the vendor-labeling-convention footgun is generic, not CFB-specific.
- **Postseason/neutral-site games mislabeled into a regular-season week index.** The data provider labels bowl/CFP games "week=1" in some seasons, silently making 24-49% of "week 1" rows postseason games and contaminating early-season priors with December outcomes; the bug hid for a while because the resulting bias had offsetting signs (openers overshoot, bowls undershoot) that averaged toward a false null. The exact bug class recurs in CBB via conference tournaments and early-season neutral-site events (Maui Invitational, Battle 4 Atlantis, PK85, etc.) and NCAA Tournament round/week ambiguity -- build the season-type/round guard from day one.
- **A grader/settlement bug that manufactures a fake result.** Settling props at a de-vigged "fair" line nobody could actually bet, rather than the real book line, manufactured a phantom push rate and inflated a headline ROI number before being caught (section 6). Generic to any props-grading pipeline.
- **A model-selection bug that let a corrupted eval fold pick the wrong model.** A filter bug silently dropped rows from one evaluation fold, and logloss-based selection then preferred the resulting broken model because it scored artificially well on the corrupted set. General ML pitfall, not sport-specific.
- **A frozen/stale data source masquerading as a real trend (INV-88).** A raw play-clock field was found frozen at the data source in a majority of one season's games, which had been feeding a spurious "pace is trending" conclusion into a production model; the fix was detection and exclusion, not modeling, and the zero-rate distribution was cleanly bimodal, proving the detection threshold wasn't arbitrary. Any new CBB data source needs a liveness/staleness audit before trend-fitting on it.

- **An aggregate gate passing while two errors canceled underneath it (INV-56).** A home/away score anti-correlation was measured wildly wrong (-0.37 vs. reality's -0.01) even though the resulting totals variance calibrated fine -- two separate offense/defense biases were canceling at the aggregate level. This is the direct motivation for the multi-level-evidence standing rule (section 4) and will recur identically in CBB (team-total calibration looking fine while offense and defense are each biased in opposite directions underneath it).
- **Home-field-advantage root cause (INV-50).** Roughly 84% of a home-field-advantage deficit traced to offensive touchdown scoring, whose model simply never had an is_home feature in its list at all -- structurally incapable of representing home-field advantage, not merely undertrained. It had previously been "fixed" by a compensating runtime shim, then explicitly reopened once that was recognized as masking the real gap rather than closing it. For CBB: audit every scoring-stage model directly for whether a home-court feature is actually present in the feature list; don't assume it's inherited from an upstream rating.
- **A seed-noise floor discovery that changed betting policy (INV-95-class).** Roughly a third of totals betting picks flipped sign between two independently-seeded halves of the same configuration, which is what drove the standing rule requiring at least 48 seeds before trusting any ROI number. Will recur identically -- a CBB engine needs its own seed-count-vs-noise study before any early ROI read is trusted.
- **Reference/production simulator drift (INV-93).** Two "twin" simulators meant to be bit-identical agreed on 0 of 160 sampled cells; roughly 19% of the divergent cells produced an identical final box score via a completely different play-by-play stream underneath -- box-score-level parity checks would have missed the drift entirely. For CBB: if a validation "reference" simulator exists alongside a fast production one, require full per-possession parity comparison, never just final-score or box-score-level identity checks.
- **Missing rare-event channels entirely, not just miscalibration of existing ones (INV-40/41).** No strip-sack/reception-fumble path existed at all for a stretch (only interceptions modeled as pass turnovers), and special-teams returns used a Gaussian approximation instead of empirical outcome pools -- gaps that stayed invisible partly because the grading oracle itself was also broken at the time (see below). For CBB: audit for entirely absent branches (shot-clock violations, technical/flagrant fouls, and-one free throws, intentional-foul end-game strategy), not just calibration of branches that already exist.
- **Endgame/clock-killing behavior (INV-39).** No state-conditioned clock-killing behavior existed initially; the eventual fix made the headline bias metric temporarily worse, because honest kneel-downs replaced compensating fake late-game snaps -- a correct fix that looks like a regression on the wrong metric. CBB's analog is four-corners/intentional-fouling/end-of-clock heave behavior, and any fix there should be judged structurally, not by whether one aggregate bias number improves immediately.
- **The grading oracle itself was corrupt (INV-44).** The "actual totals" used to grade an entire sweep were wrong on roughly 25 of 654 games (overtime-accumulation bugs; one game recorded 121 points against a true 83) -- the test data, not the model, was the bug. CBB's analog is multi-overtime accumulation and buzzer-beater/review-related scoring quirks in the ground-truth feed; verify the grading data before trusting any grading result built on it.

- **Two good fixes fighting each other at scale (INV-68).** A damping fix and a shrinkage revision each looked good alone on a small sample; combined and re-tested at full scale (654 games x 48 seeds), the shrinkage revision actively undid the damping fix's gain -- a favorable small-sample read did not replicate at scale. For CBB: validate the full stack of stacked changes together at scale, not each change in isolation on a small sample, before shipping a combined stack.
- **"Is this a bug, or the profitable side of a real market inefficiency?" (INV-98 reframe).** Sim totals ran persistently under the market in the first two weeks of two different seasons -- but checked against verified finals, the market's own opener was biased the other way, and the sim's apparent "error" was actually the profitable side of a real, exploitable market inefficiency (a documented 58.6% hit rate, +13.3% ROI on exactly that spot). This was formalized into a mandatory checkpoint before chasing any bias-vs-market to zero: check whether closing the gap would also close a real edge. Directly relevant to CBB's own early-season market inefficiencies, which are well documented to be even larger than football's given even thinner public coverage.
- **Allocation-vs-level conflation (INV-141).** A blowout-margin defect was initially assumed to be a variance/dispersion problem; per-band standard deviation actually matched real data in every band, proving the real bug was the split between favorite and underdog allocation, not the total variance. "The total is right" does not prove the split underneath it (team totals, half-by-half, or in CBB's case perhaps starter-vs-bench allocation) is also right -- check both levels independently.
- **A fully validated, gate-passing engine still lost money live (INV-134, "the board loss").** A backtested, gate-passing engine lost real money (a documented -9.2% ROI) in its first two weeks of live real-money trading -- the backtest did not predict this. Budget for a live-or-paper-trading bridge before committing real capital regardless of how clean the backtest looks, and treat the first live weeks as a distinct validation phase, not a formality.
- **The anti-patch rule.** Traced explicitly to a predecessor project's postmortem (a scalar red-zone-TD multiplier that masked a genuinely missing QB-identity feature): no post-hoc multiplicative "fixes" on sim output -- fix the root cause in the model or feature that's actually wrong. This temptation will recur the first time a CBB shot-model or foul-model shows an aggregate bias that a quick scalar could paper over.
- **Windows console encoding.** A `PYTHONIOENCODING=utf-8` environment variable was needed because the default Windows console encoding chokes on characters like "less-than-or-equal" or a minus sign in print statements -- a trivial but recurring annoyance on this exact Windows dev environment, worth fixing in CBB's tooling on day one rather than rediscovering it.
- **HANDOFF.md staleness** -- the canonical rolling handoff file silently fell behind a differently-located, more recent handoff file by project's end (section 1). Fix for CBB: one canonical current-state pointer, not "whichever file has the latest date."
- **Docs describing models that were never actually shipped**, and **long stretches of work with no version control** -- both pure process failures that directly motivated `docs/models/DOCUMENTATION_STANDARD.md`/`change_ledger.md` and the git-discipline rules in CLAUDE.md respectively. Both are cheap to prevent by adopting the documentation standard and git hygiene from day one rather than retrofitting them after months of undocumented drift, which is exactly what happened here.

**Sizing an 8-week CBB plan:**
- **Weeks 1-2**: research/architecture docs plus the data pipeline. Most of the template (doc skeleton, decision-log format, INPUTS_MAP-style free/paid audit) is directly reusable from this project; only CBB-specific content needs writing, which should compress this phase relative to the original.
- **Weeks 3-4**: core possession-based engine plus sub-models trained to a first working, ungated version -- the equivalent of this project's Phase 0/1.
- **Weeks 5-6**: the audit/gate sprint. This project's highest-value phase took roughly two concentrated weeks even with an already-working engine to audit; budget it deliberately as its own phase rather than assuming it falls out naturally from weeks 3-4, and expect it to surface CBB-specific leaks, colliders, and seed-noise floors that mirror (but are not identical to) the ones in section 8.
- **Weeks 7-8**: production pipeline (ratings refresh, roster/lineup override runbook adapted for a daily-not-weekly cadence, cloud sweep, market grading), and only if time remains, a first cautious market-facing layer. This project treated live trading as an explicit stretch goal reached in its final three days, not a core deliverable, and a CBB plan should treat it the same way -- a validated, gate-passing engine with honest market-comparison grading is the realistic 2-month deliverable; live capital deployment is a stretch goal beyond that window.
